# AI-Powered Knowledge Quiz Builder

Generate a 5-question multiple-choice quiz on any topic, take it, and get instant grading with per-question explanations. Quizzes are generated by Google Gemini, grounded with Wikipedia context, and saved per user with full history and review.

## Features

- **Topic-based generation** — type any subject, concept, or place; Gemini returns exactly 5 MCQs (A–D, one correct answer, with explanations), validated server-side before anything is saved
- **Wikipedia grounding (RAG)** — the topic is searched on Wikipedia and the article extract is injected into the prompt to improve factual accuracy; generation degrades gracefully if Wikipedia is unavailable
- **Quiz taking** — all questions on one page, live progress bar, answered indicators, sticky submit bar, session restore on refresh
- **Instant results** — animated score ring, correct/incorrect breakdown, and an explanation for every question
- **History** — searchable table of past quizzes with scores, status, and one-click review; unfinished quizzes can be resumed
- **Accounts** — JWT auth (register/login) so all data is scoped per user
- **SaaS-style UI** — collapsible sidebar navigation, breadcrumb appbar, dashboard stat cards (quizzes created, completed, average score), responsive down to mobile (drawer nav), accessible forms with show/hide password

## Run locally

### 1) Database

Requires a running MySQL/MariaDB server (XAMPP works fine).

```bash
mysql -u root -p < database/schema.sql
```

> Note: the script drops and recreates the `quiz_app` database.

### 2) Backend

```bash
cd backend
cp .env.example .env   # then fill in the values below
npm install
npm run dev
```

Backend runs on `http://localhost:3001`. The server fails fast at startup if `JWT_SECRET` is missing or too short.

| Variable | Required | Notes |
| --- | --- | --- |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` | yes | connection for the `quiz_app` DB |
| `GEMINI_API_KEY` | yes | from [Google AI Studio](https://aistudio.google.com/apikey); without it quiz generation returns 503 |
| `JWT_SECRET` | yes | min 16 chars — generate with `openssl rand -hex 32` |
| `JWT_EXPIRES_IN` | no | default `7d` |
| `PORT` | no | default `3001` |
| `CORS_ORIGIN` | no | one origin or a comma-separated list; defaults to local Vite ports |
| `NODE_ENV` | no | set `production` to hide internal details from 5xx responses |
| `TRUST_PROXY` | no | set `1` behind a reverse proxy so rate limiting sees real client IPs |
| `GEMINI_MODEL` / `GEMINI_CONTEXT_MAX_CHARS` / `GEMINI_QUOTA_RETRY_ROUNDS` | no | Gemini tuning, see `services/aiService.js` |

### 3) Frontend

```bash
cd frontend
npm install
npm run dev
```

Frontend runs on `http://localhost:5173` and proxies `/api` to the backend (configurable via `VITE_API_URL`).

## API

Base URL: `http://localhost:3001/api` — `GET /api` returns a JSON overview, `GET /api/health` is the liveness check.

| Method | Path | Description |
| --- | --- | --- |
| POST | `/auth/register` | create account → `{ token, user }` |
| POST | `/auth/login` | sign in → `{ token, user }` |
| GET | `/auth/me` | current user |
| POST | `/quizzes` | generate a quiz from `{ topic }` |
| GET | `/quizzes` | quiz history for the current user |
| GET | `/quizzes/:quizId/questions` | questions/options for taking (no answers) |
| POST | `/quizzes/:quizId/submissions` | submit answers → score + breakdown |
| GET | `/quizzes/:quizId` | full detail/review |

All `/quizzes` routes require `Authorization: Bearer <token>`. Responses use a consistent envelope: `{ success, data }` on success, `{ success: false, error: { code, message } }` on failure.

## Architecture decisions

- **Layered structure** — routes → controllers → services → models. Controllers stay thin; `quizService` orchestrates the flow (Wikipedia → Gemini → persistence); models isolate all SQL.
- **Validated AI output** — Gemini responses are parsed defensively (JSON mode with fallback, code-fence stripping) and validated against a strict shape (exactly 5 questions, A–D options, one valid correct answer). Malformed output returns a structured error and nothing is saved.
- **Atomic writes** — question inserts and quiz submissions run in DB transactions, so a failure can't leave a half-saved quiz or submission.
- **Central error handling** — every error maps to a stable error code and HTTP status in one place.

## Security

- **Answers are never exposed early** — the take-quiz and pre-submission detail endpoints exclude correct answers and explanations; they are only revealed after submission. Grading happens server-side.
- **Ownership checks** on every quiz route — accessing another user's quiz returns 403.
- **Rate limiting** — per-IP limits API-wide, with a stricter limit on login/register to slow brute-force attempts.
- **Auth hygiene** — bcrypt password hashing, uniform "invalid email or password" errors, and a constant-time-style dummy compare so response timing doesn't reveal whether an email is registered. Duplicate registration is handled by the DB unique index (no check-then-insert race).
- **Hardened HTTP layer** — helmet security headers, tight JSON body limit, strict input validation with length caps, parameterized SQL everywhere.
- **Safe failure modes** — fail-fast startup checks for required secrets; in production, 5xx responses return generic messages while full details go to server logs.

## Tradeoffs and limitations

- No automated test suite yet — verification has been manual (API-level and in-browser).
- Rate limiting is in-memory: fine for a single instance, would need a shared store (e.g. Redis) behind a load balancer.
- The JWT is stored in localStorage for simplicity; httpOnly cookies with CSRF protection would be the next step.
- Quiz generation runs inside the HTTP request (with quota-aware retries); at real scale it would move to a job queue.
